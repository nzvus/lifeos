# ADR-0057: v2's schema is schema.md, with `user_id` on every table and its own migrations in apps/v2

**Status:** accepted
**Date:** 2026-10-17

## Context
The v2 target (approved 2026-10-16) describes the schema in
`docs/spec/v2/schema.md`: a hybrid of generic facts (entries and their
values) and five specialised shapes (ADR-0053). It names v1's invariants:
every owned table has `user_id`, composite foreign keys `(id, user_id)`,
exact `numeric`, money in cents, a 30-day trash, no stored aggregates. The
engines are written (E1–E11); the converter from v1's export needs tables to
write into. Two things the spec leaves open: whether child rows (values,
lines, sets) carry `user_id` too, and where v2's migrations live before v2
has a database.

## Options considered
### A. Every table has `user_id`; every owned reference is a composite key
- Pros: one rule, no exceptions. `ownedBy` works on any table. The database
  refuses my value pointing at your food (`entry_values.ref_item_id`), or my
  line pointing at your product: v1's defence in depth, kept for the generic
  tables, where references are the most frequent.
- Cons: one uuid more per child row (values are the biggest table). Every
  insert must carry the owner, which the repositories do anyway.
### B. Child rows keyed by their parent only
- Pros: smaller rows; the schema.md text as written.
- Cons: a reference from a value or a line to another owned row could only be
  checked in code. That is the check v1 moved into the database after the
  isolation audit.
### C. Postgres row-level security instead
- Pros: isolation enforced on every query, even a hand-written one.
- Cons: ADR-0006 deferred RLS behind the `ownedBy` hook. Adopting it is a
  separate decision, and it does not replace composite keys for references.

## Decision
**A.** Isolation is the invariant v1 never broke, and v2's generic tables
hold the references (values, lines, parts) that v1 kept in typed columns.
Also decided:
- the schema lives in `apps/v2/src/core/db/schema/`, the migrations in
  `apps/v2/drizzle/` (generated by `drizzle-kit generate`, read, committed);
  every `npm test` applies them to PGlite from zero, as in v1;
- they are applied nowhere until the Neon branch `v2` exists (the developer
  creates it with the first slice that serves pages). From then on, v1's
  pipeline: rehearsed on the PR's branch, applied by the human-triggered job;
- the engines stay free of Drizzle (lint: `core/engines/**`); only
  `core/db` and the repositories use it;
- `entries.kind` is text with no foreign key: built-in kinds live in code,
  and the user's own kinds are rows checked by the same type;
- auth tables are v1's (Better Auth), in v2's own database.

Tripwire: if child rows' `user_id` turns out to cost real space or speed on
the developer's data (values over ~10 M rows), revisit B for `entry_values`
only.

## Consequences
- Every insert into a child table names the owner. The repositories take an
  `Owner` and fill it, so a test per table proves another user's row is
  refused.
- `schema.md` now says "every table", children included.
- The root CI runs v2's tests, so v2's migrations are checked on every PR
  from today, months before they meet a real database.
